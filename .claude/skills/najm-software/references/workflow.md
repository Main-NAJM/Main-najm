## 1. قراءة الطلب

اقرأ الطلب كصاحب منتج لا كمنفّذ حرفي. اكتب لنفسك سطرًا واحدًا:
**«بعد هذا التغيير، يستطيع المستخدم أن ___»**. إن لم تستطع إكماله، لم تفهم الطلب بعد —
لكن **لا تسأل عن التفاصيل التقنية**؛ استنتج من المستودع، ومن `decisions.md`، ومن السياق.

**النطاق هو ما طُلب.** لا تُوسّعه بميزات لم تُطلب، ولا تُضيّقه لأن جزءًا صعب.
والطلب المختصر («أضف صفحة العملاء») يعني الميزة كاملة: الشاشة، حالاتها الأربع،
التجاوب، الوصولية، الربط بالبيانات، والتنقّل إليها.

**«بالتفصيل» تعني التفاصيل الضمنية أيضًا.** صفحة قائمة تعني: بحث، ترتيب، حالة فارغة،
تحميل، خطأ، وفتح التفصيل. لا تنتظر أن يُملى عليك ما هو بديهي في منتج محترم.

## 2. الاستطلاع قبل الكتابة

قبل أي سطر جديد، افهم القائم — الاتّساق أهم من الكمال المعزول:

- **الرموز:** اقرأ `src/styles/global.css`. لا تخترع لونًا ولا مسافة.
- **الأنماط المتكرّرة:** ابحث عن مكوّن مشابه وقلّد بنيته وتسميته وأسلوبه.
- **الأنواع:** راجع `src/data/` قبل تعريف نوع جديد — غالبًا موجود.
- **البيانات:** راجع `firestore.rules` لتعرف الشكل والصلاحيات.

المكوّن الجديد الذي لا يشبه إخوته عيبٌ حتى لو كان أجمل منفردًا.

## 3. بطاقة القرار

إن لزمت (راجع `decisions.md` §10) — واحدة فقط، وبهذه الصيغة، وبلا مصطلح تقني:

```
القرار: <جملة واحدة بلغة المنتج>
ماذا يعني عمليًا: <ما الذي سيراه المستخدم — سطر أو سطران>
البديل لو رفضت: <سطر واحد>
موافق؟ نعم / لا
```

**لا تسأل ثم تنتظر بلا عمل.** أنجز كل ما لا يتوقّف على الجواب أولًا، ثم اطرح البطاقة
عند النقطة التي تحتاجها فعلًا. وحين يكون الجواب متوقَّعًا بوضوح — اِفترضه ونفّذ،
واذكره في التسليم.

**لا بطاقة للمراجعة.** لا تسأل «هل أكمل؟» ولا «هل الخطة مناسبة؟». نفّذ وسلّم.

## 4. التنفيذ

الترتيب الذي يقلّل إعادة العمل:

1. **البيانات والأنواع** — عرّف الشكل أولًا؛ يكشف الثغرات مبكّرًا.
2. **المنطق** — الـ hook أو الدالة، بمعزل عن الواجهة.
3. **الواجهة** — الحالة الممتلئة أولًا، ثم الفارغة والتحميل والخطأ.
4. **التجاوب** — من 320px صعودًا، لا العكس.
5. **الوصولية والصقل** — تركيز، تسميات، حركة، تباين.

**أثناء الكتابة:**
- كل شاشة جديدة تُربَط بالتنقّل — صفحة لا يمكن الوصول إليها ليست منجزة.
- كل كتابة لها حالة تحميل وحالة فشل.
- كل نص للمستخدم بالعربية.
- كل قيمة بصرية من الرموز.
- لا `TODO` ولا `FIXME` ولا كود ميت ولا `console.log` متروك.
- لا تُعلّق كودًا قديمًا «احتياطًا» — التاريخ في git.

## 5. الفحص

**آليًا** — يجب أن يمرّ قبل أي تسليم:

```bash
bash .claude/skills/najm-software/scripts/quality-gate.sh
```

يشغّل فحص الأنواع والبناء، ويرصد المخالفات الشائعة (خصائص اتجاهية، `vh`،
عروض ثابتة، ألوان خام، `:hover` بلا حماية، `any`، `console.log`، `TODO`).

**يدويًا** — لا يُغني عنه أي سكربت:

- افتح الشاشة على 320px و390px و768px و1280px (راجع مصفوفة `responsive.md` §2).
- جرّب الحالات الأربع فعليًا: امسح البيانات، أبطئ الشبكة، اقطعها، أدخل 200 صفًّا.
- تنقّل بلوحة المفاتيح من أول عنصر لآخره — التركيز مرئي في كل خطوة؟
- بدّل إلى الوضع الداكن.
- **اقرأ الفرق (diff) كاملًا بعين ناقدة** — ماذا كنت سترفض لو كنت مراجعًا؟

## 6. التسليم

بالعربية، قصيرة، بلغة المنتج. الصيغة الملزِمة:

```
## ما أُنجز
- <نقطة أو ثلاث — ما صار المستخدم قادرًا على فعله>

## قرارات اتخذتها نيابةً عنك
- <القرار> — <سبب من سطر>

## ما لم يُنجز
- <إن وُجد، مع السبب. اكتب «لا شيء» إن اكتمل كل شيء>
```

**لا** تُلصق أكوادًا. **لا** تشرح بنية الملفات ما لم يُسأل. **لا** تعدّ خطواتك.
**لا** تُبالغ: إن لم تختبر شيئًا قل ذلك؛ وإن فشل فحص فاذكره بنتيجته.

## 7. الرفع والنشر

**الفرع:** `claude/najim-software-skill-6q1xcc` (أو الفرع المخصّص في تعليمات الجلسة).
لا تدفع إلى `main` أبدًا.

```bash
git add -A
git commit -m "<وصف واضح للتغيير>"
git push -u origin <اسم الفرع>
```

- **الرسائل بالإنجليزية**، بصيغة الأمر، تصف *ماذا ولماذا* لا *كيف*.
- **كوميت واحد لكل تغيير منطقي.** لا تخلط إصلاحًا بميزة.
- **فشل الشبكة فقط** يُعاد معه المحاولة (2s، 4s، 8s، 16s). فشل آخر يُقرأ ويُفهم.
- **لا طلب دمج (PR)** إلا إن طلبه ناجم صراحةً.
- **لا نشر (`npm run deploy`)** إلا إن طلبه صراحةً — النشر فعل يراه العالم،
  ويحتاج بطاقة قرار إن لم يكن مطلوبًا نصًّا.

## 8. حين يتعذّر شيء

**أنجز كل ما عداه.** لا توقف العمل كلّه لأن جزءًا تعثّر.

ثم اذكره في «ما لم يُنجز» بثلاثة أسطر: ما هو، لماذا تعذّر، وما المطلوب لإتمامه.

**مصادر التعذّر الحقيقية:** صلاحية ناقصة، مفتاح أو سرّ غير متاح، خدمة خارجية معطّلة،
تعارض صريح مع طلب سابق. وما عدا ذلك غالبًا ليس تعذّرًا بل صعوبة — والصعوبة تُحلّ لا تُبلَّغ.

**حين يصحّح ناجم شيئًا:** اقبل التصحيح، طبّقه، وواصل. لا اعتذار مطوّل، ولا شرح لما حدث،
ولا إعادة سرد. سطر واحد يقرّ بالتغيير ثم العمل.

**حين ترى مشكلة في الطلب نفسه:** قلها في سطرين، ثم **نفّذ الطلب كما هو** تحت افتراض
معلن. تقليص النطاق قرار ناجم لا قرارك. وإن كرّر ناجم طلبه بعد تنبيهك — فهذا حسمه،
نفّذه كاملًا بلا عودة للنقاش.
