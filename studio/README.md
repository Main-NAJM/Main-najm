# استوديو بوفايدة — أداة العمل الخاصّة

المكان الذي يُجهَّز فيه كل فيديو **قبل** توليده: السيناريو، نصّ التعليق الصوتي،
موجّهات المشاهد بالإنجليزية، نصّ المنشور، ثم المشاريع والسعر.

ملف واحد مستقلّ (`index.html`) — لا بناء ولا حزم ولا خادم.

## التشغيل محلياً

```bash
npm run studio
```

## ما تفعله

1. **تكتب** السيناريو العربي، ونصّ التعليق الصوتي، وموجّهات كل مشهد بالإنجليزية،
   ونصّ المنشور — كلّها تُنسخ بضغطة.
2. **تولّد** الصور والفيديو عبر [fal.ai](https://fal.ai) من الشاشة نفسها، وتعرض
   كلفة كل مشهد بالدولار والدينار قبل أن تسعّره للزبون.

### التوليد — كيف يعمل

| | |
| --- | --- |
| المفتاح | من fal.ai ← Dashboard ← Keys، ويوضع في **الإعدادات ← التوليد** |
| أين يُحفظ | في هذا الجهاز وحده. **لا يُرفع إلى حسابك السحابي ولا إلى المستودع** |
| النموذج الافتراضي | `fal-ai/kling-video/v2.1/standard/image-to-video` — أفضل نسبة جودة إلى سعر للمنتجات |
| صورة المنتج | تُختار من الجهاز (تُصغَّر تلقائياً إلى 1280px قبل الإرسال) أو تُولَّد |
| الطلب | يمرّ بثلاث خطوات كما تفرض fal: إرسال ← سؤال عن الحال كل ثلاث ثوانٍ ← قراءة النتيجة |

**«صورة ← فيديو» لا «نصّ ← فيديو»** عن قصد: النموذج يبدأ من صورة سلعة زبونك
الحقيقية، فيخرج منتجه هو لا منتج يشبهه. وهذا هو الفرق بين إعلان يبيع وإعلان يُرفض.

### أسماء النماذج والحقول قابلة للتحرير — ولهذا سبب

fal تبدّل نماذجها وأسماء مدخلاتها بين إصدار وإصدار (`image_url` في بعضها،
`start_image_url` في غيرها). فبدل أن يتطلّب التغييرُ تعديلَ كود، يُصحَّح في خانة
داخل **الإعدادات ← إعدادات متقدّمة**. وإن ردّت fal بخطأ في المدخلات فإنها تسمّي
الحقل الناقص باسمه، والأداة تعرض ردّها كما هو.

### CORS: سؤال حُسم على جهاز حقيقي

بُنيت الأداة وشبكةُ بيئتها لا تصل إلى fal.ai، فبقي سؤال واحد معلّقاً: هل يأذن خادم
fal للمتصفّح بالاتصال المباشر؟

**الجواب: نعم.** تقرير فحص من هاتف أندرويد حقيقي أظهر ردّين بأرقام HTTP صحيحة
(`401` بلا مفتاح، `403` به) — أي أن الطلب وصل وعاد. **فلا حاجة إلى وسيط.**

ويبقى [`proxy/`](./proxy/README.md) مكتوباً لمن أراد ألّا يمرّ مفتاحه في المتصفّح
أصلاً — وهو سبب وجيه بذاته، لا حلّ لعطل.

### فحص المفتاح يشخّص، ولا يخمّن

يرسل محاولتين: واحدة بلا مفتاح وواحدة به. والفرق بينهما يفصل الأسباب:

| ما يحدث | الحكم |
| --- | --- |
| تفشل المحاولتان بلا رقم | الطلب لم يصل: حجب أو انقطاع أو CORS |
| الرسالة تذكر `balance` أو `locked`، أو `402` | المفتاح سليم والرصيد فارغ |
| `401` أو `403` بلا ذكر الرصيد | المفتاح مرفوض |
| `422` أو `400` | كل شيء سليم — فحصٌ فارغ يردّ بنقص المدخلات |

**ترتيب هذه الأسطر مقصود:** fal تردّ على نفاد الرصيد بـ`403` كما تردّ على المفتاح
المرفوض. فمن قرأ الرقم وحده اتّهم مفتاحاً سليماً وأرسل صاحبه ينسخه من جديد بلا
فائدة — وقد وقع هذا فعلاً قبل أن يُصحَّح. **الرسالة تفرّق بينهما، لا الرقم.**

والتقرير يُنسخ بضغطة، ولا يدخله المفتاح — طولُه فقط.

## الدخول — ثلاث طرق ولكلٍّ سببها

| الطريقة | ماذا تفعل | الحالة |
| --- | --- | --- |
| **بريد إلكتروني** | حساب حقيقي على Firebase. مشاريعك تُحفظ في حسابك فتتبعك بين الهاتف والحاسوب، ولا يقرؤها غيرك ولو عرف الرابط | ✅ يعمل — مُختبَر على المشروع الحيّ |
| **رقم هاتف** | نفس الشيء برسالة نصّية | ⏸ يحتاج تفعيل: Firebase Console ← Authentication ← Sign-in method ← Phone ← Enable (ورسائل SMS قد تحتاج خطّة Blaze) |
| **رمز الجهاز** | بديل بلا إنترنت: يفتح بيانات هذا الجهاز وحدها بلا مزامنة | ✅ يعمل دائماً |

رمز الجهاز موجود كي لا تُغلق الأداة في وجه صاحبها يوم تنقطع الشبكة أو يسقط تحميل
مكتبة Firebase. وهو **ستار لا قفل**.

## المزامنة السحابية

تُحفظ بيانات الاستوديو في حقل `studio` على وثيقة المستخدم `users/{uid}` — لا في
مجموعة مستقلّة تحتها.

**والسبب عملي:** القاعدة التي تسمح لصاحب الحساب بوثيقته منشورة في المشروع منذ
البداية، أمّا مجموعة جديدة فتحتاج نشر قواعد من لوحة Firebase — وهي خطوة متعبة على
الهاتف، تعثّر فيها صاحب الأداة مرّتين (مرّة ارتدّ الرابط العميق إلى صفحة المشروع،
ومرّة انتهى في **Realtime Database** وهي منتج آخر بلغة قواعد أخرى).

فما دام الموضع المسموح به يفي بالغرض، فهو الموضع. **ولا شيء عليك فعله في لوحة
Firebase.**

الكتابة بالدمج (`merge`) لأن تطبيق حرفة برو يكتب حقل `profile` على الوثيقة نفسها:
لولا الدمج لمحا كلٌّ منهما بيانات الآخر. وهذا مُختبَر على المشروع الحيّ لا على ورق —
كُتب `profile` ثم `studio` ثم قُرئا معاً فبقي كلاهما.

وتبقى قاعدة مجموعة `studio` مكتوبة في `firestore.rules` ومُختبَرة على المحاكي
(15/15). لا يحتاجها أحد اليوم، وهي جاهزة إن كبرت بيانات الاستوديو يوماً فاحتاجت
مجموعة مستقلّة.

## الخصوصية — اقرأ هذا

الصفحة منشورة على GitHub Pages، أي أن **من يعرف رابطها يفتحها ويقرأ شيفرتها**.
الذي يحمي **بياناتك** هو الحساب: قواعد Firestore تربط كل وثيقة بصاحبها، فلا يقرأ
أحدٌ مشاريعك ولو فتح الصفحة.

وما يخفي الصفحة نفسها:

- غير مربوطة من أي صفحة (`/bofaida/` لا يشير إليها، ولا الموقع في الجذر)
- تحمل `noindex, nofollow` فلا تدخل نتائج البحث

## التخزين

كل شيء في `localStorage` تحت المفتاح `bofaida.studio.v1`، ويُرفع إلى حسابك حين تدخل
بالبريد (بعد نشر القاعدة). هذا يعني:

- بلا حساب: يبقى في هذا المتصفّح وحده
- مسح بيانات الموقع يمحو النسخة المحلّية
- **خذ نسخة احتياطية** من تبويب «الإعدادات» (ملف JSON) واحفظها في مكان آمن
